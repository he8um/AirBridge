## Summary

This document records the state of AirBridge at the v0.1.0-alpha readiness checkpoint. It covers what is implemented, what is intentionally disabled, the safety posture, and the test counts as of this checkpoint.

## What Works

### Connection

- Personal access token connection check via the Airtable API.
- Permission check results (read/write/schema) are surfaced in the UI.
- Token is validated for structural completeness before any API call.
- Token is never stored; never appears in any result or log.

### Base Catalog and Schema

- List accessible bases for a given token.
- Fetch full base schema (tables, fields, field types, linked record references, select options).
- Results are read-only; no Airtable state is modified.

### Backup Planning

- Generate a backup plan from a connected base (tables, fields, record counts).
- Generate a records export plan with table ordering, linked record dependencies, pagination parameters.
- Compatibility engine classifies each field type for restore support.

### Backup Package Writing

- Run a backup job to write a `.airbridge` ZIP package to a user-chosen output path.
- Requires explicit file picker selection and the exact confirmation text `CREATE BACKUP`.
- Output path is validated before any write (extension, parent directory, traversal, existing directory).
- Token consumed to build the HTTP client; never stored or echoed in results.
- Full output path never included in the command response — filename only is returned.
- Cancellation is supported mid-job via a dedicated cancel command.

### Package Inspection

- Select and inspect a `.airbridge` package.
- Validates manifest, schema, checksums, and record entries.
- Returns filename only; the full path is never in the result or UI.
- Read-only: no files are extracted, no Airtable calls, no token required.

### Restore Dry-Run Planning

- Generate a restore plan preview from an inspected package.
- Shows tables, field compatibility, record counts, linked record ordering, and warnings.
- Read-only: no Airtable API calls, no token required, no files written.
- Full path never in result or UI.

### Restore Schema Creation Planning

- Generate a schema creation plan from a dry-run result: ordered table creation steps, field creation steps, deferred linked record fields, manual-action fields, and a linked record dependency graph.
- Read-only: no Airtable API calls, no token required, no files written.
- Table-first ordering ensures tables are created before the fields that depend on them.
- Each field is classified: CreateDirectly, CreateWithAdjustment, DeferUntilTablesExist, MetadataOnly, ManualActionRequired, or Unsupported.
- `noChangesMade` is always `true`.

### Restore Release Readiness Snapshot

- `build_restore_release_readiness_snapshot` in `restore/restore_release_readiness_snapshot.rs` — Rust-internal only. No Tauri command, no UI surface, no TypeScript path.
- Composes the post-E2E restore readiness audit and write gate into a 12-area structured readiness report.
- Returns `AlphaReadyRestoreRuntimeDisabled` only when all safety gates pass.
- **This status does NOT mean user-facing restore execution is complete or approved.**
- Runtime restore execution (RRRS-AREA-10) remains `Disabled` in all cases.
- Attachment handling (RRRS-AREA-11) remains `Disabled` in all cases.
- Product/security approval (RRRS-AREA-12) remains `PendingApproval` — no approval has been granted.
- 7 explicit pending work items (RRRS-PENDING-01 through RRRS-PENDING-07) including product decision, runtime command contract, UI design, credential handling, cleanup strategy, attachment handling, and user-facing documentation.
- 24 unit tests.

### Restore Record Import Planning

- Generate a record import batch plan from a dry-run result and schema plan: per-table batch counts, field import policies, linked record second-pass update plans, attachment policies, old-to-new record ID mapping strategy, per-table checkpoint plans, and a global retry policy.
- Read-only: no Airtable API calls, no token required, no files written. No records are created.
- Batch size: 10 records per batch (Airtable write batch limit).
- Field import policies: Include (writable fields), DeferToLinkedRecordPass (linked record fields), MetadataOnly (attachments), Skip (computed, read-only, and collaborator fields).
- Attachment policy: MetadataOnly for all attachment fields in v0.1 — file bytes are not uploaded.
- Old-to-new record ID mapping strategy is `MapSourceRecordIdToCreatedRecordId` — actual IDs are only available after first-pass record creation at execution time.
- Linked record second-pass updates are planned but not executed in this version.
- `noChangesMade` is always `true`.

### Restore Execution Gate

- Validates all preconditions: package inspected and valid, dry-run plan ready, target mode set, token provided, exact confirmation text `RESTORE BACKUP`.
- All-gates-pass returns `readyButDisabled` — write engine is not enabled.
- Token is checked for presence only; never stored or echoed.
- No Airtable API calls.
- `noChangesMade` is always `true`.

### Restore Write Engine Skeleton

- Six-phase write pipeline skeleton: `ValidateInputs`, `SchemaCreation`, `RecordCreation`, `LinkedRecordUpdates`, `AttachmentHandling`, `FinalValidation`.
- All phases are disabled; the preview surfaces phase structure and counts using inputs from the existing planning outputs.
- No token field in request or result. No Airtable API calls. `noChangesMade` always `true`. No `Succeeded` status exists in the type system.
- `evaluate_write_gate()` returns `Disabled/DisabledByProductPolicy` unconditionally — there is no enabled branch.

### Schema Write Engine Foundation

- Request plan builder turns a schema plan summary into a sequenced list of write operations: `CreateTable`, `CreateField`, `DeferLinkedField`, `ManualAction` (four ordered phases).
- Dry-run executor skeleton always consults `evaluate_write_gate()` and returns disabled.
- Tauri command `preview_schema_write_request_plan` accepts no token and returns no token. No Airtable API calls. No Airtable base, table, or field is created.
- `noChangesMade` always `true`. `networkWritesAttempted` always `false`. No `Succeeded` status.

### Record Write Engine Foundation

- Request plan builder turns a record import plan summary into a sequenced list of write operations: `CreateRecordBatch`, `UpdateLinkedRecordBatch`, `Checkpoint`, `PreserveMetadataOnlyAttachment`, `SkipComputedField` (five ordered phases).
- Dry-run executor skeleton always consults `evaluate_write_gate()` and returns disabled.
- Tauri command `preview_record_write_request_plan` accepts no token and returns no token. No Airtable API calls. No records created, updated, or deleted.
- `noChangesMade` always `true`. `networkWritesAttempted` always `false`. No raw record payloads in result. No `Succeeded` status.
- Old-to-new record ID mapping is `UnavailableUntilExecution` — linked record update operations note this explicitly.

### Credential Storage (OS Keychain)

- Optional save of the Airtable Personal Access Token to the OS keychain via Settings → Saved Credentials.
- Token stored via the `keyring` crate (v3) — macOS Keychain, Windows Credential Store, or Linux Secret Service.
- Token never returned by any of the three Tauri commands (`get_credential_storage_status`, `save_airtable_token_to_keychain`, `remove_airtable_token_from_keychain`).
- `CredentialSaveRequest` derives `Deserialize` only — cannot be serialized back; token cannot leak through any result.
- Token never in files, SQLite, `localStorage`, `sessionStorage`, history items, or logs.
- Keychain unavailable state handled safely: static messages, no token inspection, input controls hidden.
- `evaluate_write_gate()` is unaffected — credential storage does not enable restore writes.
- Saving is optional; every operation continues to accept the token directly from the user.

### Local Job History

- Recent operations are recorded in memory as `JobHistoryItem` entries: kind (ConnectionCheck, Backup, Restore), status, filename, field/table counts, timestamps.
- History surfaced in the Reports page via `JobHistoryPanel`.
- Safe summaries only: no tokens, no full paths, no record payloads, no attachment URLs.
- In-memory store only; does not persist between application restarts.
- `list_job_history` and `clear_job_history` Tauri commands are registered.

### Release Build Workflow

- `workflow_dispatch`-only GitHub Actions release workflow (`release.yml`) builds Tauri on macOS, Linux, and Windows.
- Quality gates (`npm --prefix apps/desktop run check`) run before every build.
- Artifacts named `airbridge-<version>-<OS>` are uploaded as workflow artifacts only.
- No GitHub release is created automatically; no secrets required for artifact builds.
- `"tauri:build": "tauri build"` script added to `apps/desktop/package.json`.
- `"release:check"` convenience script added to root `package.json`.

## What Is Intentionally Disabled

| Capability | Status | Reason |
|-----------|--------|--------|
| Restore write engine (live execution) | Disabled | Safety gate exists; all write foundations are planning-only |
| Live schema writes | Disabled | `preview_schema_write_request_plan` builds the plan; write gate always blocks execution |
| Live record writes | Disabled | `preview_record_write_request_plan` builds the plan; write gate always blocks execution |
| Linked record second-pass execution | Disabled | Second-pass update plan exists; execution requires write engine |
| Attachment upload | Not implemented | Metadata-only policy; file re-upload deferred |
| Restore success path | Not possible | `Succeeded` status does not exist in the type system |
| Credential storage auto-fill | Not implemented | Saved token not yet wired to connection check/backup |
| Job history persistence | Not implemented | In-memory only; SQLite-backed history deferred |
| Streaming progress events | Not implemented | UI polls; streaming deferred |
| Attachment file download (backup) | Not implemented | Metadata-only; file re-download deferred |
| Automatic retry/resume | Not implemented | Deferred; rate-limit handling is manual |
| Restore to non-empty bases | Blocked by design | Prevents destructive overwrites |
| Merge/overwrite restore | Blocked by design | Not a v0.1 scope item |

## Safety Posture

- **Optional OS keychain storage.** Users may optionally save their token to the OS keychain via Settings → Saved Credentials. The token is never stored in files, SQLite, `localStorage`, history, or logs. The saved token is not yet automatically retrieved for operations — users must still paste it manually. Saving is never required.
- **No Airtable writes outside backup execution.** Backup requires explicit file selection and exact confirmation text. Restore write engine is disabled. Schema creation and record import planners are planning-only — no tables, fields, or records are created.
- **No full paths in results or UI.** `Path::file_name()` is applied in Rust before any result is returned. No absolute directory path appears in the UI.
- **No telemetry.** No analytics, crash reporting, or network calls to non-Airtable hosts.
- **No destructive operations.** No base, table, or record deletion. No overwrite into non-empty bases.
- **Confirmation gates.** Backup requires `CREATE BACKUP`. Restore gate requires `RESTORE BACKUP`. Both are enforced at the Rust command level.
- **Package inspection is read-only.** No files extracted, no API calls, no token required.
- **Restore dry-run is read-only.** No API calls, no token required, no writes.
- **Restore schema creation plan is read-only.** No token required. No Airtable tables or fields created. `noChangesMade` always `true`.
- **Restore record import plan is read-only.** No token required. No Airtable records created. ID mapping is execution-time only. `noChangesMade` always `true`.
- **Restore write engine skeleton is read-only.** No token required. `evaluate_write_gate()` has one outcome: disabled. `noChangesMade` always `true`. No `Succeeded` status in the type system.
- **Schema write engine foundation is read-only.** No token required. No Airtable schema writes possible. `noChangesMade` always `true`. `networkWritesAttempted` always `false`.
- **Record write engine foundation is read-only.** No token required. No Airtable record writes possible. No raw record payloads in results. Old-to-new record ID mapping is execution-time only. `noChangesMade` always `true`. `networkWritesAttempted` always `false`.
- **Release workflow is manual only.** `workflow_dispatch` trigger; no push or tag auto-trigger. Artifacts uploaded to workflow run only. No GitHub release is created or published automatically. No secrets required for artifact builds.

## Alpha Readiness Gaps

The following are known gaps that do not block alpha but should be tracked:

1. Credential storage auto-fill not yet wired — users can optionally save a token to the OS keychain, but it is not automatically retrieved for connection checks or backup operations. Users must still paste the token manually when initiating an operation.
2. No restore write execution — restore gate, schema creation plan, record import plan, write engine skeleton, schema write foundation, and record write foundation are all complete; live write execution is deferred.
3. Live schema writes disabled — `preview_schema_write_request_plan` builds an ordered plan but the write gate always blocks execution.
4. Live record writes disabled — `preview_record_write_request_plan` builds an ordered plan but the write gate always blocks execution.
5. Linked record second-pass not executed — the import plan and record write plan both describe second-pass update operations; the passes themselves require the write engine.
6. Attachment upload not implemented — attachment metadata and URLs are backed up; file bytes are not re-uploaded during restore.
7. No streaming progress — backup progress is polled, not pushed.
8. No automatic retry on rate limit — the UI shows a rate-limit error; the user must retry manually.
9. Attachment metadata only at backup — attachment download URLs may expire; the backup captures the URL at time of backup only.
10. No write-permission pre-verification for restore targets — permission is verified at write time, not before.
11. `greet` command present — a Tauri scaffold command remains registered; it is harmless and unused in the UI.
12. Old-to-new record ID mapping requires execution — the record write plan describes the `UnavailableUntilExecution` strategy; actual new IDs are only available after first-pass record creation.
13. Job history does not persist between sessions — history is in-memory only; a SQLite-backed persistent store is deferred.
14. Release build artifacts have not been smoke-tested on all platforms — cross-platform `.dmg` / `.msi` / `.AppImage` installers must be verified before any public distribution.

## What Must Not Regress Before Any Alpha Release

- Token never appears in any result, log, or UI element.
- Full output/package path never appears in any result or UI element.
- No Airtable writes outside `run_backup_job`.
- `run_restore_execution` must return `readyButDisabled` — never `succeeded`.
- Schema creation plan and record import plan produce no side effects — `noChangesMade` always `true`.
- Package inspection and dry-run produce no side effects.
- Write engine skeleton produces no side effects — all phases disabled.
- Schema write foundation produces no side effects — `noChangesMade` and `networkWritesAttempted` invariants enforced.
- Record write foundation produces no side effects — `noChangesMade` and `networkWritesAttempted` invariants enforced; no raw record payloads in any result.
- `evaluate_write_gate()` must always return `Disabled/DisabledByProductPolicy` — no enabled branch.
- No `Succeeded` status exists in `RestoreWriteEngineStatus`, `SchemaWriteOperationStatus`, or `RecordWriteOperationStatus`.
- All 4094 default-suite tests must pass (2561 Rust + 1533 frontend). The 5 ignored live sandbox harnesses are excluded from the default suite.
- No prohibited terms in public files.
